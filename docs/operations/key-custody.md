# Key custody

Two interfaces, two kinds of key.

## KeyProvider (pseudonymisation)

Symmetric keys per tenant and purpose, used by the split writer to compute
keyed pseudonyms for external actors and subjects.

- Hierarchy: a root in the provider (KMS customer-managed key or a secret
  manager's transit key); per-tenant-and-purpose data keys generated by
  the provider and stored wrapped with an encryption context of tenant and
  purpose; unwrapped into writer memory on first use.
- Access: each processor's workload identity may unwrap only its purposes.
  The writer holds all; the metering projection holds billing; the
  resolver holds the identity map key.
- Rotation: never. Rotation breaks linkability across time for the same
  person. Destruction: delete the wrapped material and record
  `audit.key.destroyed`. Pseudonyms computed under a destroyed key are
  unlinkable from then on.
- Implementations: `kms`, `transit`, `local` (tests, single-node).

## Signer (digests)

An asymmetric key used by the digest job. Public key published so
`verify` can run offline. Implementations: `kms` (asymmetric sign-verify
key, digest message type), `transit` (sign endpoint), `local`.

## Resolution

Mapping a pseudonym back to a person happens through the identity map,
which is a mutable store outside the locked prefixes. The `resolve`
operation is granted to as few roles as possible and is itself recorded.
